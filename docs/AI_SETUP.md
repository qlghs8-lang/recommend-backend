## Phase 6.3: earlier-work details and bounded compound requests

This section supersedes the 6.1/6.2 routing limitations below. HTTP request/response fields, frontend, dependencies and configuration are unchanged. The legacy single-turn endpoint is unchanged. Room classification now returns exactly `requests` (1–2 operations) and `comparison` (boolean). Each operation contains the previous five fields plus nullable `referenceTurn`, nullable `referencePosition`, and a required nullable `question`. For single/comparison plans the model should emit null and the server uses the full latest question, avoiding unnecessary output tokens. Independent compound operations copy exact nonempty spans. Strict parsing rejects malformed/extra/missing/duplicate/trailing fields, invalid locators/reference bounds and unsupported operation combinations. A single operation must cover the full latest question; independent compound spans must appear in order, not overlap, and omit no non-whitespace characters. Connectors belong to an adjacent span. These checks prevent rewriting/dropping text during splitting; they do not prove that the model selected the correct semantic route.

DETAIL may select a public work from an earlier assistant answer with `referenceTurn` (1 = immediately prior assistant turn, up to 6 within the existing 12-message/12,000-character window) and `referencePosition` (1-based, up to 5; 0 only when that answer contains exactly one work). It cannot combine references with title/ID/year/media filters. Server-written ordered IDs come from verified recommendations or detail results, including the five visible choices for duplicate titles. They persist in nullable `chat_messages.content_references VARCHAR(128)` in the same transaction as the answer. They are internal, excluded from HTTP JSON, and never extracted from answer text, model knowledge or a user-authored ID. The model gets reference-slot counts alongside the already-filtered public history; the server checks the slot and re-reads current catalog data. Missing, ambiguous, out-of-window, private-list and old metadata-free references ask for explicit title/ID; deleted works get the existing honest not-found result.

Up to two independent read-only operations may combine details, own reaction lists, recommendation/personalization, or general explanation. At most one may be RECOMMEND/PERSONALIZED/EXPLAIN, preserving the five-request provider ceiling. DETAIL + an independent recommendation and two different own lists are supported. Comparisons require two DETAIL operations, both using the full latest question locally: the answer displays canonical type/date/genre/overview for each and makes no generated interpretation/winner claim. An unresolved detail stops the remaining request; comparing the same ID asks for two different works. Unsupported/foreign-owner/ambiguous goals must classify as one whole-turn denial/unsupported/clarification response, never a supported subset. Similar-to-work recommendation filters, dependent list-then-recommend filters, more than two operations and general interpretive comparisons remain clarification cases; there is no new similarity engine.

All operations share one TurnBudget, quota admission and existing owner-checked completion. Classification has a maximum of 512 output tokens within the unchanged default 800-token / 20-second turn budget; remaining generation gets only the unused allowance. Only a complete response is persisted. Any provider/query/validation failure saves neither operation. Each operation receives its own current-question span. A compound containing any private reaction list starts with the existing private-list envelope; its ENTIRE answer is removed from future model context and has no reference slots, including any public section. No reaction-list IDs/titles are newly sent to the provider. User-authored questions remain unchanged under the existing policy.

Schema rollout: the checked working configuration uses Hibernate `ddl-auto=update`, which should add the nullable column on backend relaunch. The generated MySQL ALTER is tested offline; actual live MySQL migration is unverified. Existing rows remain intact and do not acquire guessed reference IDs. If automatic update is disabled/fails, the reviewed fallback is [phase6-3-chat-references.sql](sql/phase6-3-chat-references.sql); run only if the column is absent. No live database migration was executed by Codex.

## Phase 6: local reaction-based personalization (historical baseline)

Room requests such as `내가 좋아요를 누른 장르 기반 작품 추천해줘`, `내 취향에 맞는 영화 추천해줘`, and `찜 기반 코미디 영화 추천` now use a deterministic, server-side personalized ranking. The latest question must explicitly request personalization; ordinary recommendations and reaction-status requests retain Phase 5 behavior. This is a local recommendation branch of the chat assistant: it does not call OpenAI, runs no tools, and returns zero provider token usage. The legacy single-turn endpoint is unchanged. No frontend, API shape, schema, configuration or dependency change is required; existing AI-enabled and request-quota checks still apply.

After checking room ownership, the server reads at most 100 recent LIKE/BOOKMARK/DISLIKE rows for the authenticated account, ordered by timestamp then ID. Only scalar content IDs, event types and catalog genres are read; no account metadata or VIEW/click history is used. Duplicate content/type pairs and duplicate genre labels within one record contribute once. Genre weights are LIKE +3, BOOKMARK +2 and DISLIKE -3, added across records. Existing Korean/English genre aliases are normalized. Keep at most 16 nonzero genre weights by absolute magnitude, breaking ties by genre name. These are simple explainable heuristics, not a learned model or a claim about viewing history. Older records and duplicate rows can fall outside this bounded taste window.

The parameterized JPA query excludes every work the owner currently has LIKE, BOOKMARK or DISLIKE for, including reactions older than that window. It applies movie/TV and lexical conditions from the latest question after removing supported personalization phrases. It ranks across the catalog by summed genre score, lexical relevance, rating, views and stable ID, then returns at most 12 candidates. Genre scoring uses comma-separated whole genre labels, case folding and spaces, rather than title/overview substrings. Up to three top-ranked works are selected locally and re-read from Content before rendering; missing/deleted selections still fail without saving a turn. Negative genre scores lower rank; they do not exclude every work sharing a disliked genre. Each query requests a two-second timeout, whose enforcement depends on the driver. Query output and scoring terms are bounded, but database scanning depends on catalog size.

Every result includes a server-written `추천 이유(답변 시점): ...` based on its verified catalog genres and the request's score snapshot. Missing positive preferences or a nonpositive candidate score is disclosed; fallback uses the remaining score and catalog ordering without inventing taste. An empty eligible pool returns clarification without a provider call. LIKE/DISLIKE/BOOKMARK changes are read again on the next personalized request, including requests from another owned room. There is no stored taste profile or new cross-room conversation memory. Explicitly asking for personalization again is required: an elliptical `다른 것 추천해줘` alone does not continue personalized mode or promise previously unseen recommendations.

Taste weights, source reaction IDs and explanation lines are never sent to OpenAI by this branch. Visible history keeps the answer-time explanation and requested reaction snapshots. Future provider context strips `개인화 기준(답변 시점): ...`, `추천 이유(답변 시점): ...` and the existing reaction-summary lines from assistant messages; user-authored text is unchanged. Public recommended titles and catalog facts may still appear in later conversation context. The earlier approved Phase 5 bounded reaction tool remains available for ordinary model-backed requests; its exposure scope is unchanged. No full payload/private conversation logging is added.

## Phase 5: read-only catalog and own-reaction tool calling

Room recommendations now use Responses function calling with the existing pinned Java SDK. In tool calling, the model requests a named function and JSON arguments; the server validates and executes the function, then returns facts for the next model step. The model has no database connection or SQL execution capability. The implementation follows the [official OpenAI function-calling guide](https://developers.openai.com/api/docs/guides/function-calling).

| Allowlisted function | Arguments | Result |
| --- | --- | --- |
| `search_catalog` | Exactly `query`: nonblank string, at most 200 Java UTF-16 units | At most 12 public candidates using the existing lexical retriever |
| `get_content` | Exactly `contentId`: positive integral 64-bit ID | One public candidate or `{ "found": false }` |
| `get_my_interactions` | Exactly `contentIds`: 1–12 distinct positive integral 64-bit IDs already returned in this turn | Map of requested content IDs to the authenticated user's recorded LIKE/DISLIKE/BOOKMARK states; empty arrays for no recorded states |

All three schemas use `strict: true` and `additionalProperties: false`. Server parsing independently rejects extra/duplicate fields, trailing JSON, unknown functions, non-integral/overflowing IDs, and arguments exceeding 2,048 characters. Reaction lookups additionally reject duplicate or unreturned IDs and more than 12 distinct reaction content IDs cumulatively across the whole turn. The search text is parameterized through JPA Criteria, never interpreted as SQL. Candidate DTOs retain the Phase 4 clipping limits. Queries request a two-second timeout; actual driver enforcement remains deployment-dependent.

A turn starts with the Phase 4 candidate retrieval. Empty initial retrieval still skips the provider and saves the existing clarification; query reformulation through tools is available only after a nonempty initial retrieval. Short greetings and the legacy single-turn endpoint keep their previous behavior. No frontend, endpoint, schema, environment variable or dependency changes are needed.

The model can make zero to three sequential tool calls, with at most four provider requests including final selection. Parallel calls, duplicate call IDs, unexpected output types and a function call after the limit are rejected. The fourth request forces `tool_choice: none`. `AI_MAX_OUTPUT_TOKENS` now bounds the **sum** of generated tokens over a room recommendation's whole loop, including reasoning/tool arguments; less than 16 remaining tokens stops the loop. Usage returned to the frontend sums all provider requests, including repeated input. Existing quotas/concurrency slots cover the whole turn and SDK retries remain disabled. Additional tool rounds may increase input-token cost despite the output cap.

`AI_TIMEOUT_SECONDS` supplies one generation-loop deadline, including tool execution, with remaining time applied to each provider request. The initial SQL retrieval and final revalidation/save occur outside that loop; a database driver that ignores query timeout can overrun the deadline before the post-query check. Tool JSON is capped at 24,000 characters per result; accumulated replayed reasoning is capped at 64,000 characters. At most 48 distinct candidates can be known in one turn (12 initial plus three searches of up to 12). No tool state is stored between turns.

Responses use `store: false` and replay function calls, matching `function_call_output` items and reasoning (including encrypted content) in memory within the turn, without `previous_response_id`. They are not stored in chat history or logged. Only the final server-rendered answer is saved. Catalog fields and tool results are marked as untrusted data outside fixed instructions. Initial ordinary recommendation JSON now contains zero to three `recommendations` entries with ID, verified public evidence and labelled interpretation; the legacy ID-only client method remains available. Each ID must have been returned by initial retrieval or a successful tool lookup. The server re-reads selected `Content` rows and checks evidence against current facts, preserving Phase 4 grounding and deletion checks. Tool/provider/validation failures save neither message. Ownership checks run before retrieval or tools, and network calls hold no database transaction.

## Phase 4: SQL-first catalog grounding

The room-message endpoint now retrieves real `Content` rows before recommendation generation. RAG means supplying retrieved facts as model context. Explicit short greetings/thanks keep the existing conversational reply with `catalogGrounded: false`; recommendation requests use retrieval. The existing single-turn `/api/chat/messages` endpoint keeps its general, ungrounded behavior and response shape.

`CatalogRetriever` uses a read-only JPA Criteria query, never model-written SQL. It examines at most 32 words, keeps at most eight search terms/genre aliases, and matches title, genres and overview. Korean genre aliases also match common English genre labels. Explicit movie/TV requests filter `type`; title matches rank above genre and overview matches, followed by rating, views and ID. Requests without search terms use this bounded ranking; meaningful terms with no matches do not fall back to unrelated records. A simple “다른 것 추천해줘” follow-up reuses the most recent user question in the same room. This is lexical retrieval, not semantic similarity or account-level personalization. Complex Korean morphology, exclusions, runtime/year constraints and ambiguous titles may need clarification and are not guaranteed filters.

The query returns at most 12 candidates and requests a two-second query timeout (driver enforcement is deployment-dependent). Each provider candidate contains only ID, title (200 code points), type (10), genres (200), release date and overview (400). Candidate DTOs contain no credentials, user entities, interaction history or poster URLs. Phase 5 can separately send the approved bounded reaction projection described above. These candidates are an additional bounded context block beyond the existing 12,000-unit conversation budget. All catalog text is explicitly untrusted data and stays outside fixed instructions.

The model selects zero to three IDs using Responses `text.format` with a strict JSON schema and an enum of candidate IDs, following the [official Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs). The configured model must support this format; live model compatibility remains unverified. Server parsing independently rejects unknown fields, invalid/non-integral/overflowing IDs, duplicates, extra trailing JSON and selections outside the candidate set. After generation, the server re-reads the selected rows and renders canonical titles, IDs, types, dates, genres and catalog overview excerpts as plain text. Model-written titles or free-form recommendation claims are never displayed. This intentionally favors verifiable catalog facts over free-form conversational explanations in room replies.

## Phase 3: persistent conversations

The React `/chat` page now uses authenticated conversation rooms. The server derives the owner from the validated JWT. Missing rooms and another user's rooms both return `404 CHAT_ROOM_NOT_FOUND`. Requests never accept client history or a user ID as authority. The original single-turn `POST /api/chat/messages` remains available with its existing response shape and does not save messages.

| Method / endpoint | Behavior |
| --- | --- |
| `POST /api/chat/rooms` (no body) | Create an empty room; HTTP 201 with room metadata |
| `GET /api/chat/rooms?before=<id>` | Up to 20 owned rooms, descending creation ID; `rooms`, `hasMore`, `nextBefore` |
| `GET /api/chat/rooms/{id}/messages?before=<messageId>` | Up to 40 messages, chronological within each page; `room`, `messages`, `hasMore`, `nextBefore` |
| `POST /api/chat/rooms/{id}/messages` | Body `{ "message": "..." }`; returns `room`, the two saved `messages`, `usage`, and validation-dependent `catalogGrounded` |
| `DELETE /api/chat/rooms/{id}` | Delete the owned room and all its messages; HTTP 204 |

Room metadata contains `id`, `title`, `createdAt`, `updatedAt`, `messageCount`. Messages contain `id`, `role` (`user` or `assistant`), `text`, `createdAt`. The first successful question supplies the title (up to 40 Unicode code points). Cursor IDs must be positive. Pagination uses a fixed upper bound and no unbounded `findAll` calls.

Each account may keep 100 rooms; each room may keep 200 messages (100 completed turns). A full account/room returns `409 CHAT_LIMIT`. Delete old rooms or start a new room as appropriate. Account deletion removes chat messages and rooms in the existing deletion transaction.

The provider receives the current question plus at most 12 previous messages (six complete turns) from the same owned room, with a combined 12,000 UTF-16-unit text budget. Selection retains a contiguous suffix of complete turns and never cuts a message mid-text. A turn too large for the remaining budget excludes itself and older turns. Current input still obeys `AI_MAX_INPUT_CHARS`. Fixed instructions are sent separately; stored history has only user/assistant roles. This follows the explicit-message approach in the [official OpenAI conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state). This implementation replays visible text only, not encrypted reasoning or tool items. There are no tools in this phase.

The provider call runs outside a database transaction. The server saves a question and answer atomically only after successful generation. Provider failures leave no incomplete message pair. A short room lock checks that no intervening turn was saved; a stale completion returns `409 CHAT_CHANGED`. Two concurrent generations can still incur two provider charges, but only one may commit from the same history snapshot. Deleting a room during generation prevents the late completion from restoring it. Existing quotas/timeouts apply to both endpoints together.

The UI loads the most recently created room by default, keeps the selected ID in `?room=...` for refresh, and supports room creation/selection/deletion and older-message pagination. Entering a room automatically loads its records; there is no separate record-reload button. Message bodies are rendered as plain text, not stored in browser storage. Drafts remain until successful transmission. After a network timeout or an uncertain result, reselect the current room from the room list to check saved messages before explicitly retrying: client cancellation cannot guarantee that generation or saving stopped. Request idempotency and streaming remain future hardening work.

| Environment variable | Default | Meaning |
| --- | --- | --- |

| `AI_MODEL` | empty | Explicit Responses-compatible model selection |

| `AI_GLOBAL_REQUESTS_PER_MINUTE` | `60` | Sliding one-minute quota per instance; configurable 1–600 |
