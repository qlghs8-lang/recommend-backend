## 미노출 추천 후보 정리 기능 — 2026-11-12

- 관리자 전용 `POST /api/admin/recommend-logs/cleanup` 추가. 파라미터 기본값은 `retentionDays=90`, `limit=100`, `dryRun=true`이며, 보존 기간은 30~3650일, 건수는 1~500만 허용한다. 자동 스케줄은 없다. 실제 삭제는 `dryRun=false`를 명시한 요청에서만 수행한다.
- `createdAt < cutoff`, `exposedAt IS NULL`, 연결 클릭 없음 조건을 모두 만족하는 후보만 정리한다. 노출 기록 및 과거 미노출·클릭 연결 기록은 기간과 무관하게 보존한다. 클릭 로그는 삭제하지 않는다. 이전에 확인한 과거 클릭 64건의 연결도 이 보존 조건에 포함된다.
- 응답은 `cutoff`, `candidateCount`, `deletedCount`, `dryRun`이다. candidateCount는 이번 제한 배치의 후보 수이며 전체 대상 수가 아니다. 미리보기와 실행은 독립된 시점이므로 대상이 달라질 수 있다. 실행 시 추천 로그 잠금 뒤 DELETE 조건을 재검사한다. 정리 요청은 한 트랜잭션이며 실패 시 해당 배치 전체가 롤백된다.
- 노출·클릭과 같은 추천 로그 행 잠금을 사용한다. 노출이 먼저 완료되면 보존하고, 정리가 먼저 완료되면 이후 오래된 추천 ID의 노출 요청은 기존 404를 반환한다. 30일 이상 열린 페이지의 추천 ID는 만료될 수 있으며 다시 추천을 요청해야 한다. 직접 SQL 쓰기는 서비스 잠금 계약으로 보호되지 않는다.
- 검증: backend 일반 테스트 **56개 통과**, 선택 실행 MySQL 테스트 **24개 통과**(기존 20개 + 정리/노출 양방향 경합·롤백·과거 클릭 보존 4개). H2 테스트는 미리보기 무변경, 배치 제한, 노출/클릭/최근 후보 보존, 삭제 조건 재검사, 파라미터 제한을 확인한다. MySQL은 기존 전용 빈 `recommend_concurrency_test`와 가상 데이터만 사용했다.

## 조회수·좋아요·찜 동시성 보완 — 2026-11-12

- 검증: backend 일반 테스트 **53개 통과**, 선택 실행 MySQL 테스트 **20개 통과**(기존 10개 + 신규 10개). 신규 검증은 동일/다른 회원 조회수 증가, 좋아요 멱등성, 좋아요·싫어요 배타성, 찜 두 번 토글, 조회 롤백, 삭제 전후 행동 쓰기, 관리자 정보 수정 경합을 포함한다. 공백 검사 통과. 일반 테스트는 제한 환경 Mockito 초기화 정체 후 권한 확장으로 통과했다.
- MySQL은 기존 전용 빈 recommend_concurrency_test 스키마와 가상 데이터만 사용했다. 원본 DB 및 .env 열람·변경, 프런트 수정, 커밋·푸시·배포 없음. 재현은 `python scripts/test_mysql_concurrency.py`; 일반 `mvnw.cmd test`는 MySQL 20개를 건너뛴다.

- 다음 후보: 기존 DB 스키마와 엔티티 차이 및 중복 상태 데이터의 읽기 전용 검증. 미노출 후보 로그 보존/정리 정책, 휴대폰 공유 상태 저장소, SMS/AI 공급자 선정은 남아 있다.

## 회원·콘텐츠 삭제 FK 처리 — 2026-11-11

- 다음 미완료 항목인 삭제 처리를 수정했다. 회원 탈퇴는 회원 행 잠금 후 약관·모든 행동·추천 및 클릭 로그를 정리하고 회원을 삭제한다. 관리자 콘텐츠 삭제는 해당 행동·추천 및 클릭 로그를 정리하고 콘텐츠를 삭제한다. 다른 회원·콘텐츠는 보존한다.
- 정리와 부모 삭제는 단일 트랜잭션이다. 공통 `RelatedDataDeletion`은 기존 트랜잭션을 필수로 요구하며 클릭 → 추천 → 행동 → 약관(회원만) 순으로 삭제한다. bulk JPQL 후 영속성 컨텍스트를 비워 이미 로드된 자식 엔티티 때문에 flush가 실패하는 문제도 방지했다.
- 삭제된 대상의 과거 추천·클릭 통계도 제거되는 정책이다. 회원 탈퇴의 기존 멱등 응답과 없는 콘텐츠 삭제의 기존 오류 계약은 유지했다. 업로드 파일 자동 정리는 이번 범위에 포함하지 않았다.
- 검증: backend 전체 **53개 통과**, 새 H2 통합 테스트 **3개**로 실제 FK가 있는 회원/콘텐츠 삭제, 다른 데이터 보존, 트랜잭션 롤백 시 부모·자식 복구를 검증했다. Windows CRLF를 허용한 `git -c core.whitespace=cr-at-eol diff --check` 통과. 제한 환경 Mockito 초기화 정체 후 권한 확장 실행으로 완료했다.
- **후속 검증 필요:** 실제 MySQL의 기존 스키마·FK 및 동시 쓰기/삭제 경합. 추천·클릭 로그는 물리 FK가 없는 ID 필드라 진행 중인 추천 요청이 삭제 이후 로그를 다시 저장하는 경합까지 이번 수정이 보장하지 않는다. 로그 작성 경로와 삭제 경로의 잠금 계약 또는 FK 정책을 함께 검토해야 한다. H2 결과를 MySQL 경합 검증 완료로 간주하지 않는다.
- 이번에는 실제 DB 접속·변경, `.env` 열람·변경, 프런트 수정, 커밋·푸시·배포를 하지 않았다. 기존 변경을 보존했다. 문서는 이 파일만 갱신했으며 새 마크다운 파일은 생성하지 않았다. 이후에도 사용자가 요청하지 않으면 새 마크다운 파일을 생성하지 않는다.

## 프로필 이미지 업로드 — 2026-11-11

- SMS 공급자 연동은 보류했다. `.env`는 읽거나 수정하지 않았고 운영 DB 접속·변경, 커밋·배포는 하지 않았다.
- 실제 JPEG/PNG 디코딩, 5MiB 크기 제한, 가로·세로 각각 4096 및 총 1600만 화소 제한을 적용했다. 원본 이름/MIME을 신뢰하지 않고 UUID 이름의 PNG로 재인코딩한다. SVG/GIF 및 이미지 위장 데이터는 거부한다.
- `PROFILE_UPLOAD_DIR`가 저장 루트다(기본 `./uploads`, 실행 작업 디렉터리 기준). 실제 파일은 `<루트>/profile`, 공개 URL은 `/uploads/profile/<파일명>`이다. 운영에서는 서버 프로세스만 쓰기 가능한 영속 절대 경로를 지정한다. 심볼릭 링크 등 로컬 파일시스템 변경 권한은 신뢰된 운영자에게만 부여한다.
- 기존 `C:/upload/profile` 파일을 계속 제공하려면 실행 환경에서 `PROFILE_UPLOAD_DIR=C:/upload`를 지정하거나 별도 승인 후 파일을 새 경로로 이관해야 한다. 이번 작업에서는 기존 파일에 접근하거나 이관하지 않았다. 기존 파일은 재검증하지 않았으므로 배포 전 별도 점검이 필요하다.
- multipart 요청 제한은 파일 5MB / 요청 6MB, 파일 초과 응답은 413, 유효하지 않은 이미지는 400이다. 프록시의 요청 제한도 배포 시 맞춘다.
- 프런트 이미지 URL은 Axios의 `REACT_APP_API_BASE_URL` 설정을 따른다. `/api` 같은 상대 경로도 지원하며, 리버스 프록시는 해당 경로의 `/uploads/profile/*`도 백엔드로 전달해야 한다. 기본 이미지 경로는 프런트 기본 아바타로 표시한다.
- DB 저장 실패 시 새 파일을 정리한다. 삭제는 DB 갱신 성공 후 관리 대상 UUID PNG만 정리한다. 기본/기존 이름의 파일은 보존한다. 교체 전 파일은 자동 삭제하지 않으며, 파일과 DB 간 원자적 트랜잭션은 없으므로 고아 파일의 참조 확인·보존기간 기반 정리는 후속 작업이다. 삭제 정리 실패는 경고 로그를 남긴다.
- 검증: backend 37개, frontend 19개 테스트 통과, 프런트 production build 성공. 임시 폴더 + mock 저장소 + MockMvc를 사용했다. 실제 DB, 실제 서버 multipart 파서·프록시 및 브라우저 E2E는 미검증이다. 기존 Browserslist/Node 경고가 남아 있다.

## 최신 진행 상황 — 2026-11-11 인증 기반 1차 수정

사용자가 이 문서를 보고 진행하도록 요청해 인증 기반의 독립적으로 검증 가능한 부분을 수정했다. 아래 기존 분석 기록보다 이 절이 최신 상태다. 전체 개선 계획이 완료된 것은 아니다.

### 완료

- `JwtUtil`: 고정 키 제거, `JWT_SECRET` 필수 주입, 최소 32 UTF-8 바이트 검증. 실행 환경에 안전한 새 키를 설정해야 한다. `.env` 자동 로딩은 구현하지 않았다.
- `JwtFilter`: 삭제된 사용자/빈 subject 거부, JWT 예외만 401로 처리. DB·하위 필터 예외가 인증 실패로 변환되지 않는다. User에는 비활성 필드가 없으므로 비활성 계정 정책은 추가하지 않았다.
- 가입 응답을 `RegisterResponse(id, email, nickname)`로 제한하고 로그인 콘솔 로그를 제거했다.
- 가입/비밀번호 변경에 공통 영숫자 8~72자리 정책 적용. 프런트 가입 검증·안내도 일치시켰다.
- 회원 서비스 중복은 `ConflictException` 409, 인증 정책 위반은 `ForbiddenException` 403, 없는 회원은 `ResourceNotFoundException` 404. 일반 IllegalStateException을 일괄 403 처리하던 로직 제거. DB 무결성 충돌은 내부 상세 없이 409. 오류 문자열은 UTF-8 명시. 다른 서비스의 기존 RuntimeException/400 처리는 별도 정리 대상이다.
- 프런트 Axios는 401만 세션 만료 처리. 공개 경로 `/users`와 `/login`은 정확한 경로로 비교하며, 관리자 가드도 403/서버 오류에 토큰을 삭제하지 않는다.
- `.env`, `.env.*` Git 제외 추가. 사용자 `.env`는 읽거나 변경하지 않았다.
- 실패하던 빈 SpringBootTest를 실제 JWT/서비스/MockMvc/보안 필터 테스트로 교체했다. 프런트 Jest 27이 패키지 exports를 해석하지 못하는 문제를 설치된 CJS 진입점 매핑으로 해결했다. 라이브러리 갱신 시 매핑 경로도 확인한다.

### 검증

- backend `mvnw.cmd test`: **15개 통과**. JWT 위조/만료/삭제 사용자, 실제 SecurityFilterChain 401/403/관리자 허용, 가입 응답·오류 코드, 비밀번호 검증 포함.
- front `npm.cmd test -- --watchAll=false --runInBand`: **10개 통과**. 403/409 세션 유지, 401 만료, 공개 API 예외, 보호 페이지 로그인 이동 포함.
- front `npm.cmd run build`: 성공. 기존 Browserslist 데이터 노후 및 Node deprecation 경고 존재.
- DB 저장소는 mock이며 실제 DB/전체 Boot 애플리케이션 기동/E2E 검증은 하지 않았다. 초기 Jest 캐시 권한 오류와 백엔드 Mockito 초기화 정체 후 승인된 권한으로 실행했다.
- 기존 Java 파일이 Git에도 CRLF로 저장돼 있어 줄바꿈을 보존했다. `git -c core.whitespace=cr-at-eol diff --check`로 변경 공백 검사 통과.

### 1. 인증·보안과 API 계약

- `config/JwtUtil.java`: 고정 서명 키 제거, 환경변수/설정 주입. 운영 사용 이력이 있으면 키 교체와 기존 토큰 폐기 필요.

- `service/PhoneVerificationService.java`: 인증 상태가 전화번호만으로 조회되고 가입 요청자에 연결되지 않으며 일회성 소비가 없다. 검증 티켓, 실패/발송 횟수 제한 필요.
- `controller/UserController.java`: 가입 응답에 User 엔티티를 직접 반환한다. 비밀번호 해시 등 내부 필드 없는 응답 DTO 사용.

- `service/UserService.java`: 비밀번호 변경 시 가입과 동일한 검증 정책이 없다.
- `exception/GlobalExceptionHandler.java`와 front `src/api/axiosInstance.js`: 중복 닉네임도 403이고 403이면 로그아웃된다. 401/403/409/400/404를 구분.
- 업로드 형식 검증, Windows 고정 경로, 배포용 이미지 주소, `.env` ignore도 정리 대상.

### 2. 추천·통계의 정확성

- 협업 후보 조회의 `select distinct u.content.id`로 빈도 정보가 사라져 RecommendService의 빈도 계산이 모두 1이 된다. 콘텐츠별 `count(distinct user_id)` 등으로 집계.

- 조회수 read-modify-write, 찜/좋아요 조회 후 삽입의 동시성 문제를 해결한다. VIEW 이벤트와 유일한 사용자 상태는 구분한다.

## AI 채팅 개발 방향 — 아직 미구현

공급자는 미정이다. 사용자 표현 open api는 외부 API 연동으로 해석했으며 OpenAI는 후보 예시다. 모델·예산도 확정되지 않았다.

첫 기능은 대화형 콘텐츠 추천을 제안했다. 기존 검색/추천으로 후보를 뽑고, AI는 후보 내에서 추천과 설명을 생성한다. 모델이 반환한 contentId를 서버가 검증하고 제목·이미지·평점은 DB에서 채운다.

현재 Content에는 상영시간·연령등급·OTT 제공처가 없어 해당 조건은 데이터 보강 전 보장할 수 없다.

### 제안 구조

```text
backend/chat/
  controller/ChatController
  dto/ChatMessageRequest, ChatMessageResponse
  service/ChatService, ChatContextBuilder
  provider/AiChatClient, 공급자별 Adapter
  domain/ChatConversation, ChatMessage, AiUsageLog
  repository/...
front/src/features/chat/
  ChatPanel.js, MessageList.js, ChatComposer.js
  RecommendationMessage.js, useChat.js, chatApi.js
```

### 제안 API

- POST /api/v1/chat/conversations
- POST /api/v1/chat/conversations/{id}/messages — message, clientRequestId
- GET /api/v1/chat/conversations/{id}/messages?cursor=...
- DELETE /api/v1/chat/conversations/{id}

모든 대화 접근에 인증 사용자 소유권 검사를 수행한다. 사용자 body의 userId나 role을 신뢰하지 않는다. API 키는 서버에만 둔다. 사용자별 요청/토큰/동시 실행 한도, timeout, 제한된 retry, 중복 요청 처리, 사용량 기록, 공급자 실패 시 기존 추천 fallback을 포함한다. 외부 AI 호출 중 DB 트랜잭션을 오래 유지하지 않는다. 개인정보·JWT·비밀번호는 AI에 보내지 않는다.

처음에는 JSON 응답으로 완성하고 이후 스트리밍을 추가한다. 별도 Python 서버/벡터 DB는 필요성이 확인되기 전 필수로 도입하지 않는다.
