2026-11-24. 이전 핵심 품질 개선 묶음 마감 이후 사용자가 추가 요청한 독립 기능이다. **분류·검색·주제 근거 검증과 빈 결과 안내를 구현했다. 실제 모델의 새 분류 품질 및 요리 작품 데이터 보강은 아직 미완료다.**

## 확인한 문제와 범위

사용자가 `요리 관련된 영화 추천해줘`에서는 키워드가 들어간 작품을 받았고, 이어 `흑백요리사 같이 조리나 요리 관련된 영화 추천해줘`에서는 유용한 답변을 받지 못했다고 설명했다. 원래 응답/오류 코드는 남아 있지 않아 분류 실패·미지원 안내·후보 없음·제공자 오류 중 무엇이었는지 확정하지 않는다. 기존 간헐503의 새 재현으로 세지 않는다.

기존 코드는 SETTING에 계절·배경·소재를 함께 넣고 제목/보이는 줄거리의 부분 문자열을 검사했다. 일반 주제 지시는 있었으나 명시적 소재와 유명 작품 예시의 관계, 주제를 뒷받침할 인용을 별도로 검증하지 않았다.

실제 공개 카탈로그468개를 읽기 전용으로 제한 조사했다. `음식` 언급 영화는3개였지만, 명확한 요리 이야기로 확인되지는 않았다. `요리/조리/셰프/쉐프/주방/레스토랑`의 단순 부분 문자열로는2개가 잡혔고, 둘 다 **모조리** 안의 **조리** 때문이었다(ID128 그린치, ID251 피노키오: 언스트렁). 단어 시작 경계를 적용하면 해당 검색어의 후보는0개다. 이는 한정된 검색어/제목/줄거리앞400자 조사이며 모든 잠재적 요리 작품의 부재를 의미하지 않는다.

이번에는 공개 제목·유형·줄거리와 집계만 읽었다. 회원·반응·대화 조회,앱 DB쓰기/DDL,TMDB수집,카탈로그 추가는0이다. 근거 파일은 `target/topic-recommendation-20261124/public-*.json`, `mysql-word-boundary.json`이다.

## 구현한 동작

1. 내부 조건 **TOPIC**을 추가했다. 장르·감상 분위기·계절 배경과 구분해 이야기의 활동/직업/소재를 표현한다. 기존 SETTING과 과거 저장 기록은 유지한다. 조건 총8개·사용자 원문 출처·검색어1~4개·허용 작업·기존 예산을 그대로 검증한다.
2. 요리 요청의 구체적인 검색 표현으로 요리/조리/셰프/주방 등을 분류 지시에 예시로 넣었다. 음식의 단순 등장으로 넓히지 않도록 지시한다. 동의어를 모두 아는 서버 사전이나 의미 검색을 구현한 것은 아니다.
3. **이름 있는 예시 + 명시한 소재**는 해당 소재로 검색한다. `흑백요리사 같이 조리나 요리 관련된 영화`는 RECOMMEND/MOVIE/TOPIC으로 표현하고,흑백요리사를 DB에서 식별하는 별도 상세 작업을 요구하지 않도록 지시한다. 실제 유사성·작품 사실을 검증했다고 주장하지 않는다. 소재 없이 이름만 제시한 미확인 유사성 요청은 기존 확인 불가 정책을 유지한다.
4. SQL·도구·최종 후보 검증에서 TOPIC을 함께 적용한다. 검색어는 리터럴로 이스케이프하고 Unicode 문자/숫자/밑줄 뒤의 단어 중간 일치를 제외한다. `조리한다`는 허용하고 `모조리`는 제외한다. 그룹 내 OR/그룹 간 AND,유형·시간·참조 조건을 유지한다. SQL은 REGEXP_LIKE를 사용하며 [MySQL 공식 설명](https://dev.mysql.com/doc/refman/8.0/en/regexp.html)과 [H2 공식 설명](https://h2database.com/html/functions.html#regexp_like)을 확인하고 양쪽에서 검사했다.
5. 최초 일반 주제 추천에는 **제목/보이는 줄거리에서 TOPIC 검색어와 연결되는 원문 인용**을 요구한다. 장르만 인용하거나 무관한 문장을 인용하면502/추가저장0이다. 스키마의 인용 선택지도 해당 단서가 시작하는40자 이하 조각으로 제한해 기존40자 청크 경계에서 단어가 갈리는 문제를 피한다. 필드당최대4개,Unicode surrogate 보존,모델 출력 후 원문 재검증을 유지한다. 여러 주제는 모두 후보 필터를 통과해야 하며,고정1개 인용은 최소한 하나의 주제 단서를 보여준다.
6. 후보/선택이 없으면 요청 주제와 나머지 조건을 함께 뒷받침할 제목·줄거리 근거가 현재 카탈로그에 부족하다고 안내한다. 실제 작품명을 지어내거나 무관한 인기작으로 채우지 않는다. SQL후보가0이면 추천 생성 호출도 하지 않는다.

구조화 출력으로 형식을 제한해도 스키마 밖의 업무 규칙은 애플리케이션 검증이 필요하다는 [OpenAI 공식 지침](https://developers.openai.com/api/docs/guides/structured-outputs)을 참고했다. API/모델/SDK/공개HTTP형식/DB스키마/프런트는 바꾸지 않았다. 추가 제공자 호출·재시도 경로를 만들지 않았다.
