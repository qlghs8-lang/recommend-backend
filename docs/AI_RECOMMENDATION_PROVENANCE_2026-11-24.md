# 추천 출처와 당시 개인화 근거 보존 — 2026-11-24

후속 적용/수용 완료(2026-11-24): 실제 로컬 MySQL의 누락 nullable LONGTEXT 컬럼1개를 INSTANT로 추가하고 기존 정의 유지를 확인했다. 별도 합성 MySQL·실제 JWT/HTTP·React 화면에서 추천/반복 이유/반응 변경/새로고침/오류 초안 유지를 검증했다. AI는 고정 테스트 구현이며 앞선 실제 모델 평가와 구분한다. [배포 수용 결과](AI_DEPLOYMENT_ACCEPTANCE_2026-11-24.md)를 참고한다. 아래의 MySQL/화면 미검증은 구현 당시 기록이다.

새 추천의 최초 요청과 서버가 계산한 개인화 근거를 저장하고, 후속 이유 설명에도 이어 사용하도록 구현했다. 이전 [수용 검사](AI_PERSONALIZED_RATIONALE_2026-11-24.md)의 두 미달 항목은 같은 고정 자료/실행기/채점기로 재실행해 통과했다. 기존 실패 보고서는 보존한다.

## 변경한 동작

- 개인화 추천: 당시 요청, 추천 작품 ID, 작품별 장르 합계 점수/양수 장르, 긍정 기록 존재 여부를 서버에서 생성한다. 반응 기준 원작의 제목·ID·계정·전체 장르 가중치·반응 이벤트는 저장 메타데이터에 담지 않는다. 최초 일반 추천도 요청과 추천 ID만 보존한다.
- 이유 후속: 현재 공개 카탈로그를 읽고 모델로 공개 근거를 설명하는 경로는 유지한다. 그 뒤 서버가 당시 개인화 기준을 덧붙이고 최초 추천 당시 기록이며 현재 반응과 다를 수 있음을 표시한다. 실제 모델의 내부 사고 과정을 복원하는 기능은 아니다.
- 반복 이유: 선택한 작품의 출처 메타데이터를 새 답변에도 복사한다. 원래 추천 턴이 최근12메시지/12000자 범위 밖으로 밀려나도 바로 이전 답변을 참조하면 최초 요청을 유지한다. 과거 모든 대화를 검색하거나 모델 문맥을 확대하지 않는다.
- 반응 변경: 기존 추천의 기록은 그대로 둔다. 새 개인화 추천만 현재 반응으로 다시 계산한다.
- 범위: 새 단일 추천과 그 이유 후속에 적용한다. 복합 요청은 기존 합성 답변에서 메타데이터를 전달하지 않으며, DETAIL을 사이에 둔 사슬·null인 과거 기록의 개인화 근거 재구성은 이번 범위 밖이다. 기존 공개 근거 설명은 유지하며 저장 문자열에서 점수를 추출하지 않는다.

## 저장·비노출·검증

`chat_messages.recommendation_provenance` nullable LOB에 version1 JSON을 저장한다. 원본 요청은 기존 설정의 최대 입력 상한8000자, 추천은 최대3편, 작품별 양수 장르는 최대16개/각200자, 점수 절댓값10000, 직렬화 전체24000자로 제한한다. 실제 장르 계산/기본 입력 한도는 바꾸지 않았다. JSON 중복/추가/누락 필드, 잘못된 버전/형식/ID/점수는 거절한다. null은 과거 기록으로 인정하되 비정상 non-null은 조용히 추측하지 않고 모델 호출 전 실패한다.

AiMessage에는 필드를 추가하지 않았다. 소유권 확인 후 ChatHistoryStore.Snapshot의 별도 서버 맵으로만 준비한다. ChatResponse의 내부 provenance와 public ID는 JsonIgnore로 공개 JSON에서 제외하며, 공개 대화 DTO는 기존 텍스트/ID/시간 그대로다. 모델에는 기존 공개 CatalogCandidate·최초 사용자 요청·현재 질문만 전달한다. UI 텍스트에 표시한 당시 점수/요약은 다음 모델 문맥에서 기존 스냅샷 제거 규칙으로 제거한다. 이 메타데이터를 받는 API·도구·모델 출력 스키마를 추가하지 않았다.

메시지와 메타데이터는 같은 complete 트랜잭션에서 저장하고 공개 참조 ID와 정확히 일치해야 한다. 삭제/변경된 카탈로그, 위조 인용, 타인 방, 잘못된 저장 메타데이터는 기존 실패/원자성 경계를 유지한다. 방/계정 삭제 시 해당 메시지와 함께 제거되며 별도 영구 프로필 테이블은 없다. 기본 모델·800/544토큰·20초·재시도0 유지. 키/설정/프런트엔드는 변경하지 않았다.

## Eclipse와 MySQL 적용

소스8개/새 테스트2개와 문서·SQL6개,총16파일만 실행본에 동기화했다. 덮어쓴 소스7개/문서4개는 실행본 `target/recommendation-provenance-sync-20261124`에 백업하고 복사본/원본 SHA256을 검증했다. 대상 지침·차이 확인,동기화 전 변경 감지 검사를 수행했으며 설정·무관한 변경은 보존했다.

**Eclipse F5 → 백엔드 중지·재실행**이 필요하다. 앱은 여기서 재시작하지 않았다. 두 체크아웃의 기존 ddl-auto=update를 확인했으므로 재기동 시 컬럼 추가를 시도하지만 실제 MySQL 적용은 아직 검증하지 않았다. 수동 적용이 필요하면 [SQL](sql/2026-11-24-chat-recommendation-provenance.sql)의 information_schema 조회로 대상 DB와 컬럼 유무를 먼저 확인하고, 컬럼이 없을 때만 ALTER를 실행한다. 기존 컬럼을 덮어쓰거나 과거 행을 backfill하지 않는다.

재시작 뒤 새 추천에서 `내 취향에 맞는 영화 추천해줘` → `이 영화들을 추천한 이유는 뭐야?` → `방금 이유를 설명한 첫 번째 작품은 왜 추천했어?`를 확인한다. 새로고침 뒤에도 당시 기준이 유지돼야 한다. 반응을 화면에서 변경했다면 새 추천과 과거 추천 이유를 구분해 확인한다.
