# 작품 제목 경계 보존과 모호성 확인 — 2026-11-19

지난 감사에서 `없는 작품 XYZ`와 `XYZ`가 각각 등록되어 있으면 추출된 제목에 따라 다른 상세·공개 참조가 저장됨을 확인했다. 이번 단계는 **인용된 전체 제목을 부분 문자열로 축소해 조회하는 것을 방지**하고, 인용되지 않은 제목의 범위가 모호하면 정확한 제목을 확인한다. DB 확장이나 연출 우열 안내는 별도 작업이다.

## 동작과 검증

- `'없는 작품 XYZ'의 줄거리` → 전체 제목 `없는 작품 XYZ`로 정확히 조회한다. 등록되어 있지 않으면 미발견을 안내하고 등록된 `XYZ`로 대체하지 않는다.
- 같은 질문을 모델이 `XYZ`로 축소하면 서버의 제목 경계 검사에서 조회 전에 중단하고 확인 질문을 반환한다. DB 조회 결과에 맞춰 제목을 보정하지 않는다.
- `없는 작품 XYZ의 줄거리`처럼 어떤 단어까지 제목인지 모호하면 모델은 단일 CLARIFY와 `TITLE_BOUNDARY` 사유·정확한 최신 사용자 원문 근거를 반환한다. 서버가 아래 고정 문구를 출력한다.

> 작품 제목의 범위를 확정하기 어려워요. 정확한 제목 전체를 따옴표로 묶거나 카탈로그 ID로 알려 주세요.

- `'XYZ'`처럼 정확히 지정한 짧은 제목, 일반적인 명확한 제목, 명시 ID, 서버가 관리하는 이전 작품 참조는 기존 경로를 유지한다.
- 두 제목을 명시해 비교할 때는 각각의 정확한 제목을 조회하고 두 공개 참조를 보존한다. 축소된 상세 요청이 포함된 독립 복합 요청은 다른 추천·개인 반응 목록 작업 전에 중단한다.

## 구현 범위

`TitleBoundary`는 현재 질문의 따옴표 범위만 검사하며 DB에서 제목을 추측하지 않는다. ASCII 작은/큰따옴표,곡선 작은/큰따옴표,「」,『』,〈〉,《》를 지원한다. 전체 제목의 문장부호·내부 아포스트로피를 보존하고, 따옴표 안의 앞뒤 공백은 제목 비교 시 제외한다. 기존 대소문자 무시 조회를 유지한다.

같은 문자열이 다른 인용문 안에도 있더라도, 별도의 전체 인용 또는 인용문 밖의 위치가 있으면 허용한다. 어느 언급을 대상으로 했는지는 모델이 판단한다. 한 위치가 중첩된 더 큰 인용문에 포함되면 작은 내부 제목만 선택하지 않는다. 닫히지 않은 따옴표 내부나 과도한 인용(완결 범위128개/중첩32개 초과)은 보수적으로 확인을 요구할 수 있다. 최대8000자 원문으로 제한하며 자동 번역·수정·부분 제목 검색은 하지 않는다.

이 검사는 일반 언어의 모든 인용 의미를 판정하지 않는다. 예를 들어 전체 질문을 큰따옴표로 묶고 그 안에 작은 제목을 넣으면 보수적인 확인 안내가 나올 수 있다. **비인용 제목의 의미상 모호함은 모델이 판단한다.** 서버가 모든 자연어 제목 경계를 결정하거나 어떤 모델 오분류도 막는다는 보장은 아니다. 카탈로그에 있다는 사실도 사용자가 그 작품을 의도했다는 근거로 삼지 않는다.

기존 `Clarification` enum에 TITLE_BOUNDARY를 추가했다. 새 자유 텍스트 답변/SQL/사용자 ID 필드는 없다. 단일 CLARIFY,허용 사유,최신 원문의1~100 UTF-16 단위 근거 검증을 재사용하고, 다른 경로/복합/추가 필드/과거 문장만의 근거를 거절한다. TV_DURATION_UNIT 사유와 기존 일반 CLARIFY는 유지한다.

제공자 root/composition 및 상세 locator 스키마는 유지했다. 단일 확인 사유 enum만 확장하고 route 우선 필드 순서·required/additionalProperties:false를 보존했다. [OpenAI Docs 구조화 출력 제약](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)을 확인했다. 추가 생성 호출·DB/API 변경·제공자 예산 변경은 없다.

## 실제 호출에서 발견한 큰따옴표 스키마 거절

첫39회 평가 계획은3PASS 후 큰따옴표 제목 요청에서400 `invalid_json_schema`가 발생하여 나머지35개를 NOT_RUN으로 중단했다. 이 실행은 게이트 실패로 보존하며3/3 성공으로 보고하지 않는다. 고정1개 합성 요청으로 같은 거절을 재현했고 오류의 특정 message 필드를 제한적으로 확인했다.

```text
Invalid schema for response_format 'chat_intent': In context=('properties', 'composition', 'anyOf', '2', 'properties', 'splitAfter'), " is not allowed in string literals for structured outputs (strict=true).
```

이는 이번 제공자 호출에서 관찰한 스키마 검증 결과다. 제목의 의미 판단 오류가 아니며 TITLE_BOUNDARY 사유 자체의 거절도 아니었다. 큰따옴표를 포함하는 동적 splitAfter enum 값이 원인이었다. 이전 간헐503의 원인과 동일하다고 단정하지 않는다.

경계 후보를 만드는 `ClassifierPlan.boundaries`가 큰따옴표 뒤의 **원문 접미 문자열**을 사용하도록 수정했다. 문자열을 치환하거나 질문/제목을 바꾸지 않는다. 따옴표로 끝나는 후보나 반복 때문에 안전한 고유 접미부를 만들 수 없는 경계는 제외한다. 나머지 분할점/길이/고유성/원문 손실 방지 검증은 유지한다. 인용문이 없는 원본 정답은 변경하지 않았다.

새 회귀는 splitAfter enum에 큰따옴표가 없고, `"없는 작품 XYZ"의 줄거리와 내 찜 목록`을 안전한 경계로 나눠도 두 질문의 합이 원문과 동일한지 확인한다. 수정 후 관련162개 검사와 고정 큰따옴표1요청(ACCEPTED,issues 없음)이 통과했다. 같은13개 정답으로 전체39회 평가를 새로 실행한다. 최종 회귀는 이 수정 이후 다시 수행한다.

진단은 `TitleBoundaryLiveTest#probesOnlyTheFixedDoubleQuotedSyntheticSchema`의 별도 opt-in에만 있다. 지정된 고정 합성 문장/invalid_json_schema/text.format.schema/정해진 메시지 prefix/길이/키 비포함 조건을 모두 확인하고 특정 검증 메시지만 남긴다. 예외·헤더·전체 본문·cause를 직렬화하지 않으며 운영 로그와 기존 SyntheticClassifierTrace의 오류 비기록 정책은 유지한다. 최초 진단기의 SDK 자원 처리 컴파일 오류는 close()로 수정했고 그 실패에는 API 호출이 없었다.

수정 전후 증거는 `target/title-boundary/schema-probe-before.json`, `schema-probe.json`, `acceptance-before-live-v1.json`, `acceptance-before-live.json`과 분리된 모델 보고서에 보존한다. 정답은 바꾸지 않았으며 이 진단의 통과는 모델 품질 점수가 아니다.
