# 수정 정책의 통합 대화 수용 평가

2026-11-19 시작,실제 모델 측정은11월20일 새벽까지 진행. 제품 코드·프롬프트·운영 설정·DB 스키마를 바꾸지 않는 평가 단계다. 시간 단위·제목 경계·연출 우열 안내가 실제 저장 문맥과 연결되는지 확인한다.

## 미리 고정한 기준

`conversation-acceptance-v1.json`에 두 평가 범위를 함께 선언하되 점수는 구분한다. 유료 실행 전 테스트4개와 자료1개의 SHA256을 `target/conversation-acceptance/acceptance-before-live.json`에 고정한다. 기존 자료10개와 제품 챗봇 소스 전체 해시도 보존한다.

첫 범위는 원본61문항의 **동일한 실제 모델 응답**을 두 기준에 채점하는 것이다. 원본 v1 정답·채점기·예전58/61을 유지한다. 별도 수정 정책은 rec-tv에 TV_DURATION_UNIT,detail-missing에 TITLE_BOUNDARY,clarify-ranking에 QUALITATIVE_COMPARISON 단일 확인 사유와 최신 원문 근거를 요구한다. 일반 CLARIFY만으로 성공시키지 않는다. 나머지58문항은 원본 의미·라우터 계약을 그대로 검사하고 의도하지 않은 새 사유도 거절한다. 과거 점수를 수정한 것이 아니라 새 측정의 두 점수다.

이61문항 평가는 실제 분류 모델과 제품 라우터를 쓰지만 상세/추천/목록/설명 하위 서비스는 기존 mock이다. 나머지58문항의 기존 채점기에 없던 추천 조건까지 전부 검증했다고 주장하지 않는다.

두 번째 범위는 실제 H2 서비스·저장·다음 문맥을 통과하는3개 대화14턴이다.

| 대화 | 순서 | 수용 기준 |
| --- | --- | --- |
| 시간 단위 | 인사→모호한 짧은 시리즈→회당20분 이하 추천→추천 작품 상세→전체20분 제한 | 정확한 단위 안내,TV 대표 회당10분만 추천,90분/미등록/영화 제외,실제 추천 ID 후속 참조,전체 시간 확인 불가·추가 생성 없음 |
| 제목 충돌 | 모호한 제목→인용된 전체 제목→인용된 짧은 제목→두 제목 비교→두 번째 상세 | 두 제목이 모두 저장돼 있어도 별개 행/ID 유지,이전 실제 비교 답변의 공개 참조 사용 |
| 우열 안내 | 연출 우열→명시적 장르·줄거리 비교→두 번째 상세→연기 우열 | 안내의 빈 공개 참조,저장 행 기반 대안 비교,이전 작품 참조,근거 없는 우열 생성 없음 |

매 턴 실제 ChatHistoryStore.prepare의 문맥을 모델 입력과 비교한다. 사용자/답변2개 저장,전체 이력 일치,후속 문맥의 공개 ID,grounded 표시,추천 후보,생성 횟수,반응 불변을 확인한다. DB 트랜잭션 밖에서 모델을 호출하는지도 검사한다. 정해진 숫자 조건 누락·틀린 제목·일반 확인으로의 회귀를 잡는 평가기 반례도 포함한다.

14턴을 계획대로 재생하는 오프라인 검사와,같은 대화의 **실제 모델2회 반복28턴**을 구분한다. 실제 실행에서는 분류와 유일한 회당 추천의 생성·읽기 전용 도구까지 실제 모델에 위임한다. 그 외 하위 서비스와 저장은 실제 구현이다. 고정된8개 합성 공개 작품,새 합성 사용자/방만 사용하고 애플리케이션 사용자 DB에 연결하지 않는다. 별도의 소유권 선검사와 이전 턴 근거 위조 시 부분 저장 방지 검사도 실행한다.

선언된 회당20분 조건에 추가 SHORTER_EPISODE 정렬이 붙는 것은 허용하지만 숫자 조건 누락은 거절한다. UNVERIFIABLE의 자유 문자열 값은 동일 문구를 강제하지 않고 종류·최신 원문 검증·실제 확인 불가 답변·생성 없음으로 검사한다. 이 허용은 실행 전에 고정했다.

## 실행·비용 범위

```powershell
.\mvnw.cmd test '-Dtest=ConversationAcceptanceTest,IntegratedConversationAcceptanceTest'
.\mvnw.cmd test '-Dtest=ConversationAcceptanceLiveTest' '-DchatAcceptanceLive=true'
.\mvnw.cmd test '-Dtest=IntegratedConversationAcceptanceTest#actualModelTraversesTheSameStoredConversationsTwice' '-DchatAcceptanceServicesLive=true'
.\mvnw.cmd test
```

유료 실행은 기존 CHAT_EVAL_* 별칭을 자식 셸에서만 설정·제거한다. 기존 gpt-6-luna,전체800/분류544토큰,턴20초,SDK 재시도0을 유지한다. 원본61분류+실제 서비스28분류+추천2회(각최대4응답)로 **최대97 provider 요청**이다. 429/503/504면 해당 실행의 남은 요청을 중단한다. 중간 턴 실패는 그 대화의 나머지를 NOT_RUN으로 남기며 독립 대화만 계속한다. 자동으로 정답·상한을 바꾸거나 재시도하지 않는다.

보고서는 고정 합성 입력의 분류 계획·답변·공개 ID·사용량과 제한된 provider 출력만 기록한다. 비밀·실제 사용자 대화·헤더·SDK 오류 본문은 기록하지 않는다. H2 검사 전용 요청 한도는 사용자60/전체600이며 운영 기본값은 유지한다. 한도 경계 자체는 기존 ChatServiceTest가 검사한다.

OpenAI [평가 공식 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 목적별 데이터와 자동 검증 기준을 참고했다. 모델 판단으로 정답을 다시 쓰지 않고 실행 가능한 조건·참조·저장을 검사한다. 자연스러운 표현과 광범위한 실제 사용자 만족도에는 사람의 수용 검사가 여전히 필요하다.

## 실행 결과

오프라인 평가기2개·실제 H2 대화/권한/원자성3개 통과,유료1개 조건부 건너뜀. 계획 재생14/14턴 통과. 첫 오프라인 실행은 새 평가기의 nullable 참조 위치를 삼항식에서 primitive로 변환한 오류가3개 발생했고,Integer.valueOf로 수정했다. 제품 코드나 정답을 수정한 것이 아니다. 초기 실패 로그도 보존한다.

원본61문항의 실제 모델 재측정은 **원본 v1 59/61,수정 정책60/61 — 수용 실패**다. 원본에서는 rec-tv와 detail-missing이 불일치다. 수정 정책에서는 rec-tv는 의도한 시간단위 사유로 통과하지만 detail-missing이 남았다.

실패 질문 “없는 작품 XYZ의 줄거리 알려줘”의 응답은 completed 상태의 정상 JSON이며 단일 CLARIFY,comparison=false,constraints=[]였지만 clarification 사유가 없었다. 따라서 새로운 제목 경계 안내 대신 일반 제목/ID 확인 문구로 돌아간다. 타입/전송/스키마 오류가 아니라 특정 사유 누락이다. 이 실행에 맞춰 정답을 일반 CLARIFY로 완화하거나 재실행으로 실패를 지우지 않았다.

모델 gpt-6-luna,61회 호출,보고 입력293493/출력6487토큰이다. 보고서 `target/chat-quality/acceptance-baseline-20261119145700820157100.json`,SHA256 `219423154c9d2765db54f03e0785742e5315e8d63014b7c387f00329a12d85eb`. 예전58/61은 별도의 역사적 측정으로 유지한다.

실제 모델+H2 저장 대화는 **28/28턴 통과**했다. 두 번의 회당 추천 모두 실제 생성과 근거 검증·저장을 통과했다. 분류28+추천 생성2로 provider30응답 모두 completed였고,보고 입력142148/출력3808토큰이다. 이 실행에서는 추가 함수 호출을 선택하지 않아 도구 실행의 새 실제 수용 점수로 사용하지 않는다. 도구 세션과 SQL 후보 조회는 실제 구현이며 추가 도구 호출 수용은 기존 별도 테스트와 구분한다.

보고서 `target/chat-quality/acceptance-services-live-20261119150144802373300.json`,SHA256 `51ec7660f423b1dd2e4ec9cb6f5a29b49df2b9ae7a7b64d2f28786fd7639f5dd`. 제목 경계 안내도 이 대화 반복2회에서는 통과했지만 원본61문항의 누락1회를 지우지 않는다. 동일한 단독 질문이 매번 전용 사유를 얻는다는 보장은 없다. **종합 수용은 여전히 실패**다.

이번 고정 합성 요청은91회,보고 사용량 합계 입력435641/출력10295토큰이다. 사용량은 과금 총액이 아니다. 새 자료 SHA256은 `be0b1ad5f9b11c9be7029edf24bc0c6718ef1b0c2a88df05b4ff023b7cac40ad`이며 유료 실행 전 고정본과 일치한다. 제품40파일·기존 자료10개·유료 전 평가5파일의 불변성을 최종 검증한다.

## 한계와 인계

합성8개 작품/H2 대화 검사는 MySQL 실행·HTTP 인증 전체·브라우저·실제 사용자 트래픽 검증을 대체하지 않는다. 간헐503 해결을 입증하지 않는다. 기존21x3 안정성63/63은 제품이 그대로인 이전 단계의 결과로 보존하고 이번에 중복 호출하지 않는다. 전체 기능 수용 완료나 Phase7 시작을 의미하지 않는다.

## 최종 인계

다음 단일 기능은 **제목 경계 확인 사유 누락의 진단·안정화**다. 고정61문항에서 관측한 정상 완료 일반 CLARIFY와,실제 저장 대화에서 전용 사유가 나온 결과를 함께 보존한다. 의미 분류 원인은 아직 확정하지 않았으며 출력 완성/파싱 실패로 단정하지 않는다. 다음 단계에서 좁은 반복 자료·원본 회귀를 먼저 고정해 변경 전후를 비교한다. 이번에는 제품을 추가 수정하거나 통과할 때까지 재호출하지 않았다.

실행본 지침·최초 차이·해시를 확인하고 새 테스트/자료5개를 동기화했다. 문서4개도 최종 기록 후 동기화하며 덮어쓰는 기존3개는 실행본 `target/conversation-acceptance-sync-20261119`에 원본 해시대로 백업한다. 최종9개 파일 일치와3개 백업,제품40파일/기존 자료10개/고정 평가5개 해시는 `target/conversation-acceptance/final-manifest.json`과 원본 manifest로 검증한다. 설정·비밀·관계없는 변경은 복사하지 않는다.

제품 코드는 바꾸지 않았으므로 이번 단계 때문에 백엔드를 재시작할 필요는 없다. Eclipse F5로 새 테스트·문서를 갱신하면 된다. 실제 수용 실패와 일반 회귀 성공을 혼동하지 않는다.
