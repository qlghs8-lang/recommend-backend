# 상세·추천 이유의 생성 후 카탈로그 최신성 — 2026-11-24

**수정 전 실제 OSIV/HTTP 검사12개 중4실패를 재현했고,수정 후 같은12개가 모두 통과했다.** 제품 변경은 CatalogRetriever, CatalogDetails, ChatRouter 세 파일이다. 제공자 호출·원본 앱DB 접근·스키마/프런트/설정 변경은 없다.

## 재현한 문제

JPA는 같은 요청의 EntityManager가 이미 관리하는 객체를 쿼리 결과에 재사용할 수 있다. SQL을 다시 실행했어도 생성 전 읽은 객체가 돌아오면 이전 DTO와 같다고 판단하고,이미 바뀐 줄거리·시간에 근거한 답변을 저장한다. OSIV는 HTTP 요청 동안 이 관리 범위를 유지한다.

별도로 복합 요청은 상세 정보를 먼저 렌더링한 다음 일반 설명 등 생성 작업을 수행한다. 상세 정보가 생성 중 바뀌거나 삭제되더라도 기존 라우터는 그 상세 답변을 마지막에 확인하지 않았다.

새 CatalogFreshnessAcceptanceTest는 루프백 임의 포트의 실제 Spring 앱/JWT/HTTP/OSIV와 고유 H2 메모리 DB를 사용한다. 합성 회원2명·작품2개·각 검사 새 대화방만 작성한다. 변경 주입은 제공자 경계에서 별도 JDBC 연결의 auto-commit으로 수행하며,생성 호출 중 활성 DB 트랜잭션이 없고 요청의 OSIV EntityManager가 열려 있음을 확인한다. 실제 앱DB나 실제 모델은 사용하지 않는다.

## 수정

- CatalogRetriever.detail은 기존 엔티티 선택 대신 Content 생성자 프로젝션으로 공개 스냅샷을 받는다. 기존 CatalogCandidate의 클리핑/시간 정규화와2초 쿼리 제한은 유지하고 쿼리 결과 캐시는 사용하지 않는다. 기존 초기 조회/생성 후 DTO 동등성 및 인용 검증이 실제 새 값을 비교한다.
- ChatRouter는 상세와 생성 가능한 요청이 함께 있을 때 생성 작업 뒤 상세 응답을 재조회한다. 본문·근거 여부·공개ID가 달라지면 AI_INVALID_RESPONSE/502로 전체 턴을 거절한다. 기존 ConversationService.complete 전이므로 사용자/AI 메시지가 부분 저장되지 않는다.
- CatalogDetails도 생성자 프로젝션으로 전체 필드를 조회한다. 첫 번째 수정에서는 복합 삭제만 해결되고 복합 UPDATE가 관리 객체를 다시 받아 계속 실패했다. 이 실제 재현을 근거로 추가했다. 상세의 긴 줄거리 전체,중복 제목 최대6조회/5표시,정확 제목·ID·유형·연도 조건과 기존 API는 유지한다.

변경 없는 단독 상세/두 작품 비교/반응 목록에 재조회 루프를 추가하지 않았다. 현재 최대2개 연산 중 생성 계열은1개이므로 해당 복합 요청의 추가 상세 쿼리는 최대1회다. 생성 호출·재시도·출력 토큰 한도는 늘리지 않으며 재조회도 기존 턴20초 예산 안에서 실행한다. DB 변경을 숨기거나 오래된 데이터를 새 값처럼 다시 생성하지 않는다.

## 보장 범위와 다음 단계

이 변경은 최종 재조회 시점까지 사용한 공개 정보를 확인한다. 재조회 이후 커밋 사이의 모든 변경을 잠금으로 막는 보장은 아니다. 추천 이유는 모델에 전달한 정규화된 CatalogCandidate 필드(줄거리 최대400자 등)를 비교하며,사용하지 않은 포스터·조회수까지 이유 근거의 변경으로 처리하지 않는다. 복합 상세는 실제 표시한 전체 본문을 비교한다.

실제 H2/HTTP/OSIV 동시 변경 계약을 검증했으며,이번 세션에서 MySQL·실제 모델·브라우저를 재실행하지 않았다. 재현한 문제의 원인과 무관한 임의 자연어 품질 점수나 예전 간헐503 해결로 해석하지 않는다. 다음 단일 작업은 시간 조건·후속 질문의 화면/운영 환경 통합 수용이다. 별도 요청 전에는 시작하지 않는다. 남은 최종 회귀/평가 정리와 TMDB 추가 보강·Phase7·선택적 벡터 검색은 별도다.
