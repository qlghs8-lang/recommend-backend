# 토큰 폐기 정책 — 2026-11-11

> 후속 갱신: 2026-11-11 사용자 요청으로 로컬 `localhost:3306/myproject`에는 백업·복원 사전 검증 후 필요한 스키마 변경을 적용했다. [적용 결과](database-migration-20261111.md)를 참조한다. 아래 미적용 설명은 작업 당시 기록이며 다른 환경의 적용 여부는 확인하지 않았다.

## 동작

- JWT 유효기간은 기존과 같이 1시간이다. 서명·만료 외에 `uid`(회원 ID), `ver`(토큰 버전), 이메일과 현재 DB 계정을 매 요청 비교한다. 누락된 claim이 있는 구형 토큰도 401이다. 같은 이메일로 재가입해도 회원 ID가 달라 이전 토큰은 거부된다.
- `POST /logout`은 인증된 계정의 **모든 기기 토큰**을 폐기한다. 프런트 버튼도 이를 표시한다. 단일 기기 로그아웃/refresh token은 구현하지 않았다.
- `PUT /user/password` 성공은 비밀번호 저장과 버전 증가를 같은 트랜잭션으로 처리한다. 현재 비밀번호 불일치/새 비밀번호 정책 위반 시 버전을 바꾸지 않는다. 성공 후 프런트는 세션을 지우고 로그인 화면으로 이동한다.
- `users.token_version`을 원자적으로 증가시키므로 프로세스 재시작이나 다중 인스턴스에서도 같은 DB를 사용하는 한 폐기 상태가 유지된다. 일반 엔티티 저장에서는 이 컬럼을 갱신할 수 없게 해 오래된 프로필 저장이 폐기를 되돌리지 못한다.
- 비밀번호 변경은 회원 행을 잠그고 현재 비밀번호를 검사한다. 로그인과 폐기가 겹쳐 발급된 이전 버전 토큰은 이후 요청에서 거부된다. 이미 인증 필터를 통과하여 실행 중인 요청은 취소하지 않는다.
- Spring Security 기본 LogoutFilter를 비활성화해 컨트롤러의 폐기 처리가 실행되도록 했다.
- 로그아웃 서버 오류 시 프런트는 실패를 알리고 세션을 보존해 재시도를 허용한다. 이미 401인 토큰은 로컬에서 제거한다. 다른 기기는 다음 API 요청의 401에서 로그인 화면으로 전환된다.

## 배포 준비

운영 DB에는 이번 작업에서 연결하지 않았다. 아래 SQL은 검토용 예시이며 실행하지 않았다.

```sql
ALTER TABLE users ADD COLUMN token_version BIGINT NOT NULL DEFAULT 0;
```

실제 스키마에 컬럼이 없는지 먼저 확인하고 배포 절차에서 적용한다. `ddl-auto=update`에 의존해 운영 변경을 자동 수행하지 않는다. 신규/기존 회원의 초기 버전은 0이다. 구형 토큰에는 claim이 없으므로 배포 시 전체 재로그인이 필요하다. 구버전 백엔드 인스턴스는 폐기 정책을 적용하지 않으므로 혼합 운영하지 않고 모든 인스턴스를 함께 전환한다. 프런트도 함께 반영한다. 이전 추천 작업의 `exposed_at` 마이그레이션은 별도로 필요하다.

## 검증 범위

- 실제 JWT와 필터: 정상/위조/만료/삭제 계정, 버전 불일치, 구형 claim 누락, 동일 이메일의 다른 회원 ID를 검증한다.
- 실제 SecurityFilterChain: 인증 없는 로그아웃은 401, 인증된 로그아웃은 컨트롤러의 회원 서비스 호출을 검증한다.
- H2와 실제 JPQL: 비밀번호 변경·로그아웃 버전 누적, 비밀번호 해시 저장, 실패 시 유지, 오래된 엔티티 저장 후 폐기 유지. 이 테스트의 트랜잭션은 테스트가 제공한다.
- 프런트: 서버 응답 전 세션 유지, 성공/401 정리, 500 재시도 가능, 비밀번호 변경 성공/실패 세션 처리를 검증한다.
- 실제 MySQL 잠금 경합·마이그레이션·서비스 트랜잭션 장애 주입 및 양 서버 브라우저 E2E는 미검증이다. 회원/콘텐츠 삭제 FK 검증은 다음 작업이다.
