# 종합 추천 품질 평가 기준 v1 — 1단계 고정 명세

2026-11-25 Asia/Seoul. **모든 제품 성능 지표는 NOT_MEASURED**다. 이 문서는 평가 설계이며 실제 모델/서비스 평가 실행기나 합격 보고서가 아니다. [데이터 조사](AI_DATA_LANDSCAPE_2026-11-25.md)와 함께 1단계를 구성한다. 기존 평가 JSON·정답·실패 이력·과거 점수는 보존한다.

## 무엇을 평가하는가

`사용자 요청/대화 → 의도와 조건 → 후보 검색 → 줄거리 비교·선정 → 사실/조건 검증 → 화면 답변`

모든 질문을 장르 하나로 바꾸거나 예시 단어 사전을 계속 늘리는 것을 목표로 삼지 않는다. **명시적인 필수조건**(유형·시간·연도·포함/제외 장르·작품 제외)과 **의미상 요구**(중심 소재·활동·직업·관계),**선호**(분위기·감상 상황)를 구분한다. 소재도 요청의 핵심이며 문자열 필터를 반드시 써야 한다는 뜻은 아니다. 분위기에서 추론한 장르는 선호 단서로 활용할 수 있지만 사용자 명시 필수장르로 바꾸지 않는다.

‘인용이 실제 원문에 있다’는 사실 검사이고,‘그 줄거리가 이 사람의 요청에 잘 맞는다’는 적합성 판단이다. 한 단어가 인용에 있다는 이유만으로 두 번째 판단을 통과시키지 않는다. 소재가 여러 개면 각 축의 중심성과 조합을 모두 본다. 예시 작품은 비교할 축을 해석하되 미확인 작품 사실을 모델 기억으로 덧붙이지 않는다.

JSON의 `expected.hard`는 **평가 의미 명세**이며 제품의 내부 enum/계획 형식이 아니다. `semantic_targets`는 중심 소재/관계/선호를 평가할 축이고 무시해도 되는 조건 목록이 아니다. 예를 들어 central:cooking은 음식의 단순 등장으로 통과 불가다. 문구·동의어·추론 장르의 정확한 일치는 강제하지 않는다. `reference`/`removed`로 다음 턴의 참조 범위와 해제 조건을 명시한다.

별도 검증은 다른 파일에 봉인·해시 고정하지만 같은 저장소에서 읽을 수 있으므로 **비공개/완전 블라인드 검증이라고 주장하지 않는다**. 이번에는 질문 설계와 형태 검증만 했고 제품에 맞춘 실행/수정은 하지 않았다. 향후 개선 작업자는 개발 파일만 사용하고, 검증 담당자가 검증 파일을 실행·채점한다. 검증 문항을 보고 수정하면 그 문항은 개발로 이동해 v2의 새 질문으로 교체하고 v1 결과를 보존한다. 최초 성능 기준값을 위한 검증 결과는 2단계에서 봉인하고 이후 단계에는 유형별 집계만 전달한다.

현재 질문들은 사전 의미 명세를 갖지만 카탈로그 전체 정답은 아직 없다. `EVIDENCE_DEPENDENT`는 근거가 있으면 추천,없으면 정직한 부족 안내라는 뜻이며 빈 결과를 자동 정답으로 인정하는 표식이 아니다. `CLARIFY_*`는 모호한 축만 질문하고,`UNVERIFIABLE_EXPLAIN`은 확인 불가 이유를 알리며 보장하지 않아야 한다. 유형을 생략한 요청은 MOVIE/TV 모두 허용하며 유형 확인 질문을 필수로 하지 않는다.

다중 턴은 실제 이전 응답의 공개 ID를 사용한다. 앞 턴에 두 번째 작품이 없으면 그 지시를 지어내지 않고 확인해야 한다. 기대 위치를 만들기 위해 모델이 반드시3개 추천하도록 강제하지 않는다. 앞 턴의 실패가 뒤 턴의 참조 부재를 만들면 전체 대화는 실패로 남기고,뒤 턴 단독 해석은 별도 진단한다. 개인화에는 격리된 가상 계정·가상 반응·신뢰 가능한 ‘봤음’ 선언만 쓰며 VIEW 한 번을 완주로 단정하지 않는다. 실제 회원/대화/비공개 반응을 평가 파일로 추출하지 않는다.

## 정답 근거와 자동/사람 판정

1. 코드와 카탈로그의 SHA-256,질문 버전,모델,예산,실행 환경을 고정한다. 원본 줄거리 전체와 모델에 보이는400자 범위를 모두 보존한다. 생성 응답은 합성 질문에 한해서 평가 환경에 제한 저장하고 토큰·키·헤더·개인 기록은 남기지 않는다.
2. 모델 출력을 보기 전에 질문별 독립 후보 풀을 만든다. 조사 단어 묶음,장르,사전 읽기 검토,다른 의미 단서로 확보한 작품의 합집합을 사용한다. 현재 검색 결과만 정답으로 삼지 않는다. 우선 최대36개/질문을 검토하고 출처·미검토 수를 남긴다. 양성/음성/부분 사례와 **직접 단어가 없는 관련 사례**를 포함한다.
3. 사람 검토자는 요청축·작품 전체 줄거리·보이는400자·필수조건을 보고 관련성을 0/1/2로 평가한다. 0=무관/충돌,1=부분적 연관 또는 정보 불충분,2=핵심 요청에 적합한 서사 근거가 있음. 각 점수에 원문 근거·해석·판단 불가 이유를 붙인다. 소재 두 개 중 하나만 맞으면2점 아님. 분위기/스포일러는 별도 축으로 판단한다.
4. 사람 한 명이 전부 검토하고 다른 검토자가 모든 음성/부분/모호 사례와 나머지의20%를 독립 재검토한다. 불일치는 합의 또는 UNKNOWN으로 남긴다. 이번 Codex 시드는 준비 자료일 뿐 이 요건을 충족한 라벨이 아니다. 사람 확보 전 의미 품질 게이트는 UNJUDGED다.
5. 후보 풀은 전체 카탈로그 정답이 아니다. 출력에서 처음 본 작품도 독립 채점하고 미검토 작품을 오답/정답으로 자동 대입하지 않는다. 부정·빈 결과를 확정하려면 해당 질문의468개를 전수 의미 검토하거나 검증 가능한 메타데이터 모순을 입증한다. 미검토 범위가 있으면 NO_EVIDENCE_IN_REVIEW_SCOPE다.
6. 자동 검사는 실제 ID/유형/연도/구조화 시간/null/장르/신뢰 참조·제외/원문 인용/소유권/저장 원자성/예산을 확인한다. **자동 사실 통과와 사람 의미 통과를 각각 기록**한다. 전체 줄거리에는 근거가 있는데400자에는 없으면 CONTEXT_TRUNCATION으로 구분한다.

‘실제 작품 사실’은 이번 스냅샷의 저장 필드 기준이다. 외부 공식 출처와의 정확성·최신성을 전수 검증했다는 뜻은 아니다. 완전 무폭력/아동 적합/현재 OTT처럼 필드가 없는 조건은 보장 불가로 판정한다.

Recall은 독립 검토 풀 기준 **pooled recall**이고 카탈로그 전체 Recall로 부르지 않는다. G가 비어 있거나 사람이 미채점하면 N/A 또는 UNJUDGED로 표시한다. 한 긍정 시드만 분모로 삼아 ‘검색률100%’라 발표하지 않는다. micro(전체 작품/턴)와 macro(질문/소재별 동일 가중치)를 모두 보고한다. 조건없는 요청·개인화·복합 각 갈래는 따로 집계하고 같은 작품의 중복 채점 단위를 명시한다.

선정 자체의 효과는 `선정 작품 적합성 | 후보에2점작품 있음`으로도 계산한다. 답할 수 없을 때 정직한 안내는 안전한 동작으로 기록하되 답변 가능한 추천의 성공 분모를 없애는 수단으로 쓰지 않는다. 공급자 오류·미실행을 성공으로 세지 않고 의미 품질은 채점 가능한 수와 총선택 수를 함께 보고한다. 연쇄 실패는 최초 원인과 파급 실패를 모두 남긴다.

## 실패 단계를 분리하는 기록

각 턴에 아래 구조로 평가 전용 결과를 남긴다. 현재 제품 로그를 늘리거나 비공개 대화를 기록하라는 지시가 아니다.

`caseId,split,repeat,turn,corpusHash,codeHash,catalogHash,model,budget,expectedState,actualState,initialCandidateIds,toolCandidateIds,selectedIds,referenceState,autoChecks,semanticLabels,errorStage,errorCause,status,latencyByStage,usage,costKnown,costEstimate`

| 단계/원인 | 판정 증거 |
|---|---|
| DATA_METADATA_MISSING | 필요한 시간/등급/출처 필드가 없음. 모델 추정으로 보충 금지 |
| DATA_NO_SUPPORTED_MATCH | 전수 의미 검토 또는 결정적 필수조건 검증으로 적합 작품이 없음. 부분 조사만이면 NO_EVIDENCE_IN_REVIEW_SCOPE |
| INTERPRETATION | 입력 의도/명시조건을 누락·가짜 추가하거나 분위기를 필수장르로 강제. SQL 검색 실패와 구분 |
| RETRIEVAL_FILTER / RETRIEVAL_RANK | 올바른 의도와 독립2점작품이 있으나 필터 또는 상위후보 절단으로 제외. SQL 단계별 후보 수/ID 확인 필요 |
| CONTEXT_TRUNCATION | 저장 전체 줄거리에는 충분한 근거가 있으나 앞400자에 없어 모델이 못 봄 |
| SELECTION | 보이는 후보 중2점작품이 있는데 무관한 작품 또는 빈 선택. 후보 풀을 못 받았다면 이 원인으로 세지 않음 |
| VALIDATION / ANSWER | 생성 ID·인용·필수조건 위반,요청 축 누락,동일 설명 반복. 서버가 거절하면 검증 성공과 사용자 응답 실패를 동시에 기록 |
| CONTEXT_STATE / PRIVACY | 조건 유지/해제·참조·당시근거·소유권의 오류. 실제 개인정보로 재현하지 않음 |
| PROVIDER / INFRA / UNKNOWN | 429/503/timeout/DB 장애/원인 확인 불가. 빈 결과로 둔갑시키지 않음 |

두 원인이 겹치면 최초 실패 단계와 보조 원인을 모두 기록한다. 예: 미등록 시간 때문에 관련 작품이 빠졌으면 데이터 부족,시간이 맞는데 잘못된 장르 추론으로 빠졌으면 해석 오류다. 현재 빈 응답 문구만 보고 DATA_NO_SUPPORTED_MATCH로 분류하지 않는다.

## 2단계 실행 설계와 한도 — 이번에는 실행하지 않음

- 먼저 외부호출0으로 질문/라벨/스냅샷과 현재 SQL 후보를 검토한다. 제품 수정 없이 현재 동작을 계측할 평가용 방법을 만든다. 기존61문항의 분류 정확도를 이60턴의 종합 점수로 전용하지 않는다.
- 첫 유료 파일럿은 **개발 D01–D12 각1회,12턴까지만** 제안한다. 독립 단일 요청이므로 분류1회+최대4회 선정/도구응답=최대5회/턴,최대60요청. 실제 코드와 계측으로 재확인하고 초과 전에 중단한다. 모델·별도 평가 환경·통화 지출 상한을 정하기 전 실행하지 않는다. 이 문서는 유료 실행 승인이 아니다.
- 전체 개발36턴/검증24턴은 단계별 독립 실행하고,다중 턴은 새 합성 방에서 순서대로 진행한다. 복합 요청은 갈래별 생성 때문에 단일 턴 최대5회 공식을 그대로 쓰지 않는다. 전체 실행기에서 실제 호출 수·공유 토큰·시간 상한을 먼저 계산하고 고정한다. 반복은 최초측정1회 후 불안정성 확인을 위해 최대2회로 별도 예산화한다. 검증 질문을 골라 통과 사례만 실행하지 않는다.
- 평가의 초기 제안 설정: 턴 전체20초·공유 출력2048토큰,도구≤3회/선정,SDK재시도0,순차1개. 현재 앱 설정을 읽어 이 값이라고 주장하지 않는다. 서로 다른 예산/모델의 점수를 섞지 않는다. 입력 토큰/비용은 출력 상한만으로 제한되지 않으므로 요청 전 입력 크기와 최악 비용도 확인한다.
- 달러 상한은 아직 정하지 않았다. 2단계 실제 평가 요청 시 모델의 공식 현재 단가를 확인하고 최악 총비용/호출 수를 제시해 그 요청의 승인 범위 내에서 진행한다. 키는 기존 `CHAT_EVAL_*` 비공개 환경 경로를 사용하고 채팅에 요구하지 않는다. 가격/사용량을 모르면 비용은 UNKNOWN이며0달러로 쓰지 않는다.
- 429/503/504,공유 예산/지출 상한 초과 시 추가 호출을 중단하고 나머지는 NOT_RUN. 자동 재실행으로 유리한 응답을 고르지 않는다. 성공 지연과 실패 지연을 분리하되 실패율을 숨기지 않는다.
- 최초 라벨/품질 검토는 최대36개×24개 개발 단일질문=864쌍의 상한으로 시작하고,후속·별도 검증의 근거 풀은 따로 고정한다. 전체 전수 라벨링 완료를 이번에 약속하거나 수행한 것으로 쓰지 않는다. 음성 질문 전수 검토가 안 되면 부족 원인은 UNKNOWN이다.

2단계 결과물은 기준값·실패 단계·미채점/미실행 범위·지연·비용 보고서다. 결과가 나빠도 현재 제품을 먼저 수정하지 않는다. 3단계 메타데이터 보강,4단계 검색·선정 개선은 각각 새 요청에서 진행한다.
